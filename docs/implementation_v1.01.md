# Code Palette v1.01 実装指示

> 注記（2026-08-02 オーナー承認）:
> - 本文中の「Code Palette」は製品「Chord Palette / コードパレット」を指す。
> - 他の仕様文書と矛盾する場合は、最新の文書を優先する。
> - Phase 0 調査の結果、実行時に MIDI プロトコル（Sequencer / Sampler / MIDI Channel / CC64）は
>   使用していないことを確認済み。該当項目は Performance Engine の `NoteEvent` と
>   ネイティブ `NoteStrike` に読み替えて適用する。

## あなたの役割
あなたはCode PaletteのシニアiOSエンジニア兼、MIDI伴奏エンジン設計者です。
今回は、いきなり大規模な再設計を行うのではなく、既存アプリを調査したうえで、安全にv1.01へ更新してください。
最優先事項は次の3点です。
1. 再生の安定性
2. 現在の伴奏品質の改善
3. 将来の伴奏エンジン拡張に耐えられる内部構造
UIのシンプルさを壊さないでください。
## 重要な作業原則
- 既存コードを確認せずに実装を推測しない
- 既存機能を破壊する全面書き換えをしない
- 変更前に影響範囲を整理する
- 一度に大量の機能を追加しない
- コンパイルエラーを残さない
- 既存の課金、保存、再生、コード編集機能を壊さない
- 不明点を推測で埋めず、コード上の根拠を示す
- 音楽的な変更には、聴感上の狙いを記録する
- MIDIや音声素材を無断取得・収録しない

# Phase 1：再生安定性の改善
## 目的
30〜60分に一度発生することがある「低音だけが鳴る」等の再生異常を調査し、再現性と診断性を高める。
## 実施内容
- 再生状態を一元管理する
- 複数の再生開始処理が重複しないようにする
- パターン切り替え時の古いイベントを確実に停止する
- MIDIノートのNote OnとNote Offの不整合を確認する
- 音源、Sampler、AudioUnit、Sequencer等の再初期化条件を確認する
- トラックごとのMute、Volume、MIDI Channelを確認する
- バックグラウンド・フォアグラウンド遷移を確認する
- Audio Session interruptionを確認する
- Route changeを確認する
- メモリ解放や参照切れを確認する
- 連続再生、停止、コード変更、パターン変更のストレステストを追加する
## 診断ログ
Debugビルドで、以下を追跡できるログを追加してください。
- 再生開始時刻
- 再生停止時刻
- 現在のパターン
- BPM
- 各トラックのイベント数
- 各トラックの音域
- 各トラックのMIDI Channel
- 音源ロード状態
- Audio Engine状態
- Sequencer状態
- パターン変更回数
- エラー・割り込み・Route Change
Releaseビルドでは過剰なログを出さないでください。
# Phase 2：伴奏生成モデルの整理
## 目的
現在の伴奏生成処理を、将来のBallad、Band、City、Dance、R&Bへ拡張できる構造に近づける。
ただし、v1.01では既存UIへ5スタイルを無理に追加しない。
## 推奨する概念
既存構造と整合する場合、以下に相当する責務へ分割してください。
### ChordProgression
コード、拍数、小節、転回情報を保持する。
### AccompanimentStyle
伴奏スタイルを表す。
将来拡張候補：
- ballad
- band
- city
- dance
- rnb
### RhythmFeel
リズムフィールを表す。
将来拡張候補：
- straight
- shuffle
- swing
### InstrumentRole
パートの役割を表す。
例：
- drums
- bass
- piano
- guitar
- strings
### AccompanimentPattern
コード名そのものではなく、コードに対する相対情報を持つ。
例：
- 拍内位置
- 音価
- ベロシティ
- コード構成音の役割
- オクターブ
- 発音確率
- アクセント
- アーティキュレーション
### PatternRenderer
コード進行、BPM、スタイル、パターンからMIDIイベントへ変換する。
### HumanizationProfile
パート別に次を保持する。
- timingAmount
- velocityAmount
- durationAmount
- deterministicSeed
既存実装と合わない場合、名前や分割方法を無理に合わせる必要はありません。
重要なのは責務を明確にし、UIとMIDI生成ロジックを密結合させないことです。
# Phase 3：Humanize改善
## 目的
単調さを減らしつつ、演奏を崩さない。
## 要件
### 再現可能性
同じコード進行、同じスタイル、同じシードでは、基本的に同じ結果を生成する。
再生するたびに全く別の演奏へ変化させない。
### パート別設定
全パートへ同じHumanizeを適用しない。
例：
- ドラム：タイミング小、ベロシティ中
- ベース：タイミング小、ベロシティ小〜中
- ピアノ：タイミング中、ベロシティ中
- ギター：ストローク内の微小な時間差
- ストリングス：タイミング極小、音価とダイナミクス重視
### コードグループ
コードを構成する音を完全に独立してランダム移動させない。
同時発音のまとまりを保持しつつ、必要に応じてごく小さなロール感を加える。
### BPM依存
ミリ秒固定だけでなく、BPMに応じた上限調整を行う。
速い曲で揺れすぎないようにする。
### クリップ処理
以下を保証する。
- ベロシティは有効範囲内
- Note OffがNote Onより前にならない
- 小節境界を不自然に越えない
- 次のコードと不必要に重ならない
- 負の時刻を作らない
# Phase 4：ベロシティ改善
## 目的
一定ベロシティによる機械的な印象を減らす。
## 実装原則
ランダム値だけで強弱を決めない。
次の要素を組み合わせる。
- 拍位置
- 強拍と弱拍
- フレーズ先頭
- フレーズ終端
- 音域
- パート
- コード内の音の役割
- セクションのエネルギー
- 同型反復時の小さな変化
## 例
ピアノ伴奏では、すべてのコード音を同じベロシティにせず、トップノートをわずかに目立たせる選択肢を持たせる。
ベースでは、すべての音に大きなランダム差を付けず、拍とフレーズに基づいて自然な差を付ける。
ドラムでは、スネア、キック、ハイハットで個別のアクセント規則を持たせる。
# Phase 5：音価改善
## 目的
すべての音が同じ長さで鳴る単調さを軽減する。
## 実装内容
- パターンごとにgate ratioを持たせる
- レガート、通常、短音を区別する
- 次のコード開始前に必要な余白を確保する
- ベースの短音と持続音を使い分ける
- ピアノのペダル的な重なりを制御する
- リズム伴奏では音価を短めにする
- バラード系では持続を長めにする
サステイン処理が存在する場合、Note OffとCC64の役割を混同しないでください。
# Phase 6：ボイシング改善
## 目的
コードが変わるたびに不自然な大跳躍が起きることを減らす。
## 実装内容
現在のコードと次のコードの候補ボイシングを作成し、次のコストが小さいものを選ぶ。
- 各声部の移動量
- 最大跳躍
- 音域外への逸脱
- 低音域の密集
- トップノートの不自然な動き
- 同音の過剰な重複
## 原則
- 共通音を可能な範囲で保持する
- 近い転回形を優先する
- ルートを必ず最下音に置く必要はない
- ベースパートがある場合、ピアノ左手のルート重複を減らす
- 音色に応じた適正音域を将来設定できる構造にする
# Phase 7：ベース伴奏改善
## 目的
低音を鳴らすだけではなく、曲を前へ進めるベースへ改善する。
## v1.01の最低要件
既存パターンを壊さず、少なくとも以下を扱える構造にする。
- Root
- Root + Fifth
- Octave
- Passing Note
- Approach Note
## 制約
- すべてのコードで同じ動きを適用しない
- 次のコードのルートを考慮する
- 不自然な大跳躍を避ける
- 音域を制限する
- コード外音は経過音またはアプローチ音として短く使用する
- 強拍では原則として安定音を優先する
v1.01でパターン数を大量に増やすより、少数のパターンの完成度を上げてください。
# Phase 8：フレーズ変化
## 目的
同じ1小節パターンの完全なコピーが延々と続く状態を減らす。
## 最小実装
4小節単位を基本に、次のような軽微な変化を導入できる構造にする。
- 1小節目：基本形
- 2小節目：基本形
- 3小節目：小さな変化
- 4小節目：次へつなぐ変化
変化例：
- 最終拍の音を減らす
- ベースに短いアプローチ音を追加する
- コードのトップノートを変更する
- ドラムフィルを軽く入れる
- 音価を短くして次の小節へつなぐ
ランダムにフィルを入れず、フレーズ位置に基づいて決定してください。
# Phase 9：伴奏品質評価ツール
## 目的
変更前後を毎回同じ条件で比較できるようにする。
## 固定テスト進行
少なくとも以下をテストケースとして用意してください。
### Test A
C - G - Am - F
4/4、120 BPM
### Test B
Cmaj7 - Am7 - Dm7 - G7
4/4、100 BPM
### Test C
Am - F - C - G
4/4、140 BPM
### Test D
Dm7 - G7 - Cmaj7 - A7
4/4、90 BPM
## 出力
可能であれば、Debug用に次を出力できるようにする。
- MIDIファイル
- イベント一覧JSON
- 各パートのノート数
- ベロシティ平均・標準偏差
- ノート長平均
- 音域
- タイミング偏差
- コード外音数
- Note On / Note Off不整合
- 最大同時発音数
音声レンダリングが既存環境で容易にできる場合だけ、比較用音声書き出しを検討してください。
大規模な外部依存は追加しないでください。
# Phase 10：自動テスト
以下をテストしてください。
## MIDI整合性
- 全Note Onに対応するNote Offがある
- ベロシティが範囲内
- ノート番号が範囲内
- 負の開始時刻がない
- 音価が正
- イベントが指定小節範囲を大きく外れない
## 決定性
同じ入力とシードから、同じイベントが生成される。
## コード対応
メジャー、マイナー、7th、maj7、m7等の既存対応コードで生成に失敗しない。
## ストレス
- 100回連続で再生・停止
- 100回パターン変更
- BPMを連続変更
- コードを再生中に変更
- バックグラウンド復帰
- 音源切り替え
テストできない項目は、できない理由と手動確認手順を記載してください。
# Phase 11：UX改善
## v1.01の原則
大規模な画面変更はしない。
以下を確認する。
- 初回起動時に何をすればよいか分かるか
- コード追加から再生まで迷わないか
- 再生中か停止中か分かるか
- パターン変更が音へ反映されたことが分かるか
- 無料機能とPro機能の区別が過剰に邪魔になっていないか
- iPhoneとiPadでレイアウトが崩れないか
- 小さい文字やタップしづらい領域がないか
チュートリアルを増やすより、画面を見れば操作が分かる状態を優先してください。
# Phase 12：MIDIデータベースの土台
## v1.01で行うこと
市販曲のMIDIを大量収集することではない。
まず、合法的に利用できるオリジナルまたは許諾済みMIDIを登録できる内部フォーマットを作る。
## 登録項目の候補
- id
- name
- sourceType
- license
- style
- rhythmFeel
- timeSignature
- bpmRange
- instrumentRole
- patternLengthBeats
- notes
- velocityProfile
- durationProfile
- accentMap
- tags
- qualityRating
- createdAt
- updatedAt
- version
## 重要事項
生のMIDIをそのままアプリのロジックへ密結合させない。
可能な限り以下へ変換する。
- 拍に対する相対位置
- コード構成音に対する相対度数
- 相対オクターブ
- 相対ベロシティ
- 相対音価
これにより、任意のキーやコード進行へ移植できる構造にする。

# v1.01の受入条件
以下をすべて満たすこと。
- アプリが正常にビルドできる
- 既存の主要機能が動作する
- コード進行を作成・編集・再生できる
- 課金状態が壊れていない
- 保存済みデータが可能な範囲で維持される
- 低音だけが鳴る問題について、修正または診断性向上が行われている
- 同じ入力で安定した伴奏を生成できる
- ベロシティ、音価、タイミングのいずれかが明確に改善されている
- MIDIイベントの整合性テストを通過する
- UIのシンプルさを損なっていない
- 著作権上問題のあるデータを追加していない

以下の順番を守ってください。

2. 実装計画
3. 再生不具合調査
4. 診断ログ追加
5. 自動テスト追加

7. Humanize改善
8. ベロシティ改善
9. 音価改善
10. ボイシング・ベース改善
