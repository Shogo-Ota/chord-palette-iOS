### 再生中のリズム切り替えについて

切り替えは**次の小節を待たず、その場で**反映される。ネイティブ側は `plan` をロック下で丸ごと差し替えるので、古いノートの予約が残ることはない。

拍位置は `rescaleBeats` で新しい拍子へ換算してから渡している。4小節のループはワルツで 12 拍、6/8 で 24 拍、4/4 で 16 拍と長さが違うため、拍数をそのまま渡すと折り返し先がずれて進行が別のコードへ飛ぶ（2026-07-26 に修正）。

小節頭まで待ってから切り替える挙動にするにはネイティブ側で差し替えを未来のフレームへ予約する必要があり、build 6 の範囲外。

### 既知の小さな挙動（ブロッカーではない）

シャッフルとスウィングで、スウィングした裏拍のコードが次の表拍へ最大 0.14 拍だけ食い込む。`timeBeat` にはスウィング分の遅れが乗るのに、`durationBeat` はストレートのグリッド幅（`nominalBeat * gate`）で決まるため。同音が一瞬重なるがアタックが少し厚くなる程度で、音が途切れたり鍵盤が残ったりはしない。他の 11 種では重なりゼロ。

提出直前に音を変えたくないので build 6 では触らない。次回アップデートで、ゲートを実際の次オンセットまでの間隔で測るように直す候補。

### 提出手順（build 5 の審査結果で分岐）

どちらの経路でも、先に上の実機チェックリストを終えておく。

**build 5 が承認・リリースされた場合**（想定する本線）

1. ASC で新しいバージョン **1.0.1** を作成する。リリース済みのバージョンに新しいビルドを足すことはできないため、ビルド番号を上げるだけでは提出できない
2. `app.json` の `version` を `1.0.1` に上げる（`buildNumber` は手で触らない。下記参照）
3. `eas build --platform ios --profile production` → `eas submit --platform ios`
4. EAS が書き換えた `app.json` をコミットする
5. 説明文を `docs/app-store-listing.md` §4 の最新版に差し替える（プリセット名が入っている）
6. 審査提出

**build 5 が差し戻された場合**

`version` は `1.0.0` のままでよい。上の 1 と 2 を飛ばし、3 から実行する。

#### ビルド番号は手で上げない

`eas.json` は production に `autoIncrement: true` を持ち、`cli.appVersionSource` は `local`。つまり **EAS がビルド前に `app.json` の `ios.buildNumber` を +1 して、そのファイルを書き換える**。

したがって `app.json` の値は「次に出す番号」ではなく **「最後に出した番号」**。過去の `chore(app): bump iOS buildNumber to N` コミットは、EAS が書いた結果を後から記録したもの。

- ビルド前の `app.json` は `5`（= build 5 が出ている状態）
- `eas build --profile production` を実行すると 6 になり、build 6 が出る
- ビルド後、書き換わった `app.json` をコミットする

手で 6 に上げてからビルドすると 7 が出る。2026-07-26 に一度これをやりかけたので、ここに残す。

## 4. クリティカルパスとリスク

1. **App Store 審査（最重要）**: 通常数日、初回や課金絡みで長引くことあり。**7/25提出**が事実上のデッドライン。遅れる要因（IAP設定不備・プライバシー・メタデータ）を M5 までに潰す。
2. **RevenueCat × IAP**: App Store Connect の非消費型商品作成→「送信準備完了」状態、契約/税務/口座の «有効» が前提。Sandbox テスターも必要。ここが詰まると審査に出せない。
3. **オーディオ品質**: MVPは合成ドラムで出す想定（サンプルドラムはV2）。音圧・スウィングの聴感を実機で早めに確認。
4. **動画書き出し負荷**: 60秒 1080×1920 の生成時間・発熱・メモリを実機で確認（要件§12）。
5. **Windows開発**: ネイティブ不具合の解析が遅くなりがち。EAS ビルド待ち時間を計画に織り込む。
